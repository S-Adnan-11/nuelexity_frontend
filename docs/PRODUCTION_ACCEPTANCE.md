# Restricted production acceptance and full-beta launch

This procedure describes later, separately authorized actions. The current local About task authorizes no upload, settings change, live AI/search call or launch. Use the existing [manual Pages procedure](CLOUDFLARE_PAGES_RELEASE.md) for the upload controls and public-information stage.

### Prepare an authorized live acceptance candidate

Preparation, permission to run a restricted live test, completed production acceptance and permission to open the beta are separate decisions. **Never set `productionAcceptanceComplete: true` to obtain the first live test artifact.** It remains false until the actual tests pass for the recorded revision/configuration.

1. Finish actual Google confirmation and record `googleBrandingVerified: true` only from the owner's evidence. Complete the public-policy/hosting and APP provider/transfer requirements and record their flags truthfully. These requirements remain enforced for an acceptance candidate; only completed production acceptance is deferred. No flag or external setting is changed by the candidate command.
2. Obtain the owner's explicit authorization for a named revision, exact test origin, testers, test window, permitted settings/upload actions and rollback plan. Authorization for this local task grants none of those actions. Live AI/search calls need separate, bounded authorization within available free allowances, with no paid fallback, retries or automatic replay. Keep the limited informational release available until a restricted candidate is authorized.
3. Before any candidate upload, establish and verify actual access controls for research, account, sign-in and callback routes on the intended origin **and every alternate Pages deployment hostname**. For example, inspect the account's available Cloudflare Access application/policies under **Zero Trust → Access controls → Applications**, including [path/hostname coverage](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/) and tester access through the unchanged OAuth callback. See the official [self-hosted Access application procedure](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/). The [Pages preview access toggle](https://developers.cloudflare.com/pages/configuration/preview-deployments/#customize-preview-deployments-access) covers preview deployments; it does not by itself protect the project pages.dev hostname or custom domain. Do not assume the free account has a configured control. A secret URL, preview branch, `noindex`, hidden link or disabled automatic deployment is not access control. If isolation cannot be established without an unapproved or paid change, keep the candidate local. Preserve unauthenticated public information/Google review access. Test the restrictions signed out before allowing any tester through.
4. With that separate authorization recorded, keep `productionAcceptanceComplete: false` and run from the repository root:

   ```sh
   npm run check
   npm run pages:acceptance -- --live-test-authorized
   npm run audit:release
   ```

   `--live-test-authorized` records the operator's deliberate command invocation; it does not obtain approval or verify external restrictions. The command checks all other full-app prerequisites before and after building, validates the existing four public settings/security artifact, and writes only `pages-acceptance-dist/`. It does not upload, set acceptance true or open the beta. Without the authorization argument or other prerequisite evidence it fails closed and removes stale candidate output. `pages-review/` remains a local fixture and is never an upload source; `pages-dist/` remains reserved for the final gate. Keep candidate artifacts private and outside Git.
5. Inspect and digest the candidate, record its source revision, settings, artifact digest and intended origin privately, then use the separately authorized manual Direct Upload procedure with **only `pages-acceptance-dist/`**, while the tested restrictions remain in force. An upload makes content live even when restricted; it is not authorized by preparing the command. Record the actual deployment ID and verify headers, routing and signed-out exclusion on that deployment. Preview-host results cannot establish production-origin OAuth/Turnstile acceptance. If production-origin testing requires temporarily replacing the limited release, authorize that exact switch, restrictions, restoration artifact and time window first. Do not change actual callbacks to make a preview test pass.

### Run production acceptance, then decide whether to open the beta

On the authorized, restricted deployment, record expected/actual results, tester/date, origin, revision, settings, artifact digest and deployment ID for each item:

- HTTPS, home/About/legal/footer anchors, theme/keyboard/mobile behavior, assets, sitemap/canonical, real 404s and Pages hostname indexing controls; public information remains readable without authentication or Turnstile.
- Real GitHub and confirmed Google sign-in, cancel/error/return flows and the unchanged production callback; owned conversation deep-link refresh, account separation, sign-out and stale-storage cleanup, and private `no-store`/`noindex` behavior. Use only dedicated adult test accounts and non-sensitive test data; never record tokens or private conversations in evidence.
- Actual backend-origin acceptance and guest Turnstile hostname/action/secret pairing, same-tab pass continuity/reuse, expiry/reverification, coordinated backend startup and server rejection of invalid passes. These checks do not need an AI/search call.
- Durable fail-closed quota enforcement, cancellation and data isolation using the existing fake/offline checks; where live-path proof is required, perform only the exact separately authorized guest/signed-in search scope. Verify streaming, sources, Stop and permitted model access without automatic retries or paid calls. An unperformed required check stays incomplete; local fakes do not substitute for real provider/production integration.
- Physical mobile keyboards/safe areas, Safari and a real screen reader where required by the acceptance plan. Local Chrome/Firefox evidence does not imply those checks occurred.

If a required check fails or is not performed, keep `productionAcceptanceComplete: false`, retain restrictions, and restore the approved limited release if the test window ends. Record the precise failure and repeat only affected checks after a fix under appropriate authorization.

Only after the actual required tests pass may the owner record `productionAcceptanceComplete: true` for the tested revision/configuration. Then run `npm run check`, `npm run build:pages`, `npm run release:check` and `npm run audit:release`; inspect the final `pages-dist/`. If runtime code, public settings or hosting controls differ from the tested candidate, repeat affected acceptance on the new artifact rather than inheriting the old result. Record the final revision/digest and smoke-check the actual final installation while access remains restricted.

**Opening full beta requires a separate explicit owner launch decision after acceptance.** Only then remove the temporary test restrictions through the authorized controls, verify the intended public/private access behavior, and record the launch deployment/time. No successful local build, completed candidate upload, passing test suite or policy approval grants that launch permission. Current acceptance/Google/provider flags remain unchanged and incomplete; no live test or external action is part of this task.
